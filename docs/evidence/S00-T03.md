## Current platform decision

The product owner's Vercel/Supabase decision supersedes the earlier Hostinger/MySQL result. Local infrastructure now
uses two PostgreSQL 15.8 services to mirror the two-project Supabase boundary. The old MySQL volumes were not deleted.

## Files changed

- `compose.yaml` — two pinned PostgreSQL services with separate databases, credentials, volumes, ports and internal
  Docker networks.
- `.env.example` — separate local PostgreSQL URLs and separate corporate/clinical Supabase variables.
- `pyproject.toml` and `uv.lock` — asyncpg replaces asyncmy.
- API sessions — SQLAlchemy `NullPool` avoids multiplying connection pools in serverless instances.

## Commands and results

```text

docker compose config

docker compose exec -T corporate-db psql -U corporate_app -d budimind_corporate -c "select current_database(), current_user;"
docker compose exec -T clinical-db psql -U clinical_app -d budimind_clinical -c "select current_database(), current_user;"
```

- Lock resolution removed asyncmy and added asyncpg 0.31.0.
- Compose resolved `postgres:15.8-bookworm` on separate internal networks and persistent volumes.
- `budimind-corporate-db` and `budimind-clinical-db` both reported healthy.
- Identity checks returned only the intended database/user pairs: `budimind_corporate`/`corporate_app` and
  `budimind_clinical`/`clinical_app`.
- Baseline migration marker `0001_baseline` was applied and read back through `psql` in both containers.
- Docker volume inspection confirmed both earlier MySQL volumes and both new PostgreSQL volumes remain present.
- `pnpm db:migrate` now falls back to the matching local Docker service when this managed Windows/Docker host boundary
  refuses the published port. A migration, guarded reset, and second migration all passed; hosted Supabase migration
  evidence remains a separate cloud-project task.
