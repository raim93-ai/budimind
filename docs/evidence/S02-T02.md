# S02-T02 — Identity adapter and server sessions

Status: COMPLETE

Implemented for both isolated APIs:

- Supabase Auth access tokens are introspected through `/auth/v1/user` with the plane-specific publishable key. The
  server secret and user-editable metadata are not used for authentication or authorization.
- A deterministic fake identity adapter supports only `development`/`test` and rejects any other environment.
- Verified-email and active, plane-local `private.app_actor` checks are required before session issuance.
- Opaque browser sessions are stored only as SHA-256 hashes, expire server-side, and support revocation and single-use,
  concurrency-safe rotation.
- Protected browser routes accept only the opaque session cookie after the initial provider-token exchange.
- Session cookies are `HttpOnly`, `Secure`, and `SameSite=Lax`; all auth responses use
  `Cache-Control: private, no-store`. State-changing rotation and logout require an exact double-submit CSRF
  cookie/header pair.
- Corporate and clinical sessions use independent databases. Tests prove that identities and session tokens from one
  plane are denied by the other.

The Python suite passed verified-email, cookie attributes, non-cacheable auth responses, bearer-token rejection after
exchange, CSRF denial, rotation, simultaneous-rotation single-use behavior, replay, expiry, logout, token hashing,
wrong-plane actor lookup, wrong-plane session lookup, and production-fake rejection.

Docker Desktop 4.90.0 does not publish host ports for containers attached only to `internal: true` networks. The
`python:test` command therefore detects unavailable default localhost test databases and uses a digest-pinned,
short-lived uv container with a read-only repository mount. That runner joins both plane-specific internal networks for
the cross-plane denial tests and is removed after the run. Custom database URLs never trigger the fallback. The two
database services remain on separate internal networks; no cloud resource, real-person data, or external side effect is
used.

Known limit: the hosted Supabase identity path requires the later deployment-stage project credentials and remains
unexecuted. Cloud deployment is still prohibited until the repository queue reaches the deployment stage.
